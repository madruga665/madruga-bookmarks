# Implementation Plan: Bookmark Tagging System

**Branch**: `010-bookmark-tags` | **Date**: 2026-08-16 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `specs/010-bookmark-tags/spec.md`

## Summary

Implement the comprehensive Bookmark Tagging System:
1. **Domain & Palette Foundation**: `TagPalette` (deterministic pastel color hashing for tags) and extension helpers on `BookmarkEntity` (`tagList`, `toTagString()`).
2. **Neobrutalism UI Components**: `NeobrutalistTagChip` (with remove/selection states) and `NeobrutalistTagInput` (interactive tag creation with Enter/comma delimiter and remove button).
3. **Bookmark Save Flow Integration**: Update `SaveBookmarkViewModel` and `SaveBookmarkBottomSheet` to allow adding/removing tags during initial link capture.
4. **Search Screen Filter Integration**: Update `SearchViewModel` and `SearchScreen` with interactive horizontal tag filter chip bar combining tag filters with text queries.
5. **Bookmark Cards & Details Integration**: Render tag badges on `NeobrutalistBookmarkCard` and dynamic tag management on `BookmarkDetailScreen`.
6. **Localization & Quality Verification**: Add bilingual string resources (`en` and `pt-BR`) and full unit test coverage.

## Architectural Decision Records

### ADR-001: ViewModel-Layer Tag Filtering (FR-010)

**Context**: The spec (FR-010) states that "the search engine (BookmarkRepository.searchBookmarks or DAO) MUST evaluate tags in addition to title, URL, and folder name." The original plan assumed a DAO-level tag evaluation. However, the implementation evaluates tags entirely in the `SearchViewModel`'s `combine` operator at the ViewModel layer.

**Decision**: Tag filtering remains at the ViewModel layer.

**Rationale**:
1. **Simplicity**: The `BookmarkEntity.tags` field is stored as a comma-separated string in Room. Implementing a DAO `@Query` with `LIKE` or `GLOB` operators for tag matching would require complex SQL string parsing that is fragile and hard to maintain.
2. **Reactive Architecture**: The ViewModel already subscribes to `allBookmarks` and `collections` as `Flow<List<...>>`. Combining these flows in the ViewModel layer allows reactive filtering without additional DAO queries.
3. **Performance**: Tag filtering is in-memory on a local dataset that fits comfortably in memory (<1000 bookmarks). The `<100ms` performance target is easily met with in-memory filtering, as confirmed by the test suite.
4. **Consistency**: Text search (title, URL, description, collection name) and tag search use the same combine operator, ensuring consistent AND-combined results.

**Tradeoffs**: If the dataset grows beyond local memory (future cloud sync with thousands of bookmarks), a DAO-level tag index should be introduced. For now, the ViewModel-layer approach satisfies all constitution principles and performance requirements.
